# Astraea III Architecture v0.1

## 1. Mission

Astraea turns a human research question into traceable, reviewable knowledge that can be reused across projects and fields. It optimizes for evidence fidelity, provenance, intellectual honesty, user control, and evolution across model providers.

The existing vault's capture → refinement → indexing → application flow remains the knowledge-facing backbone:

`note/fleet/` and `note/lit/` → `note/atomic/` → `field/` → `project/`

Astraea Core coordinates this flow. It is an orchestrator and policy boundary, not another researcher and not an autonomous personality.

## 2. Boundaries and ownership

### In scope

- Research jobs, task decomposition, worker coordination, validation, approvals, and run state.
- Reading permitted vault files and external source material exposed through approved tools.
- Producing draft research artifacts, evidence records, atomic notes, synthesis notes, and audit records.
- Git-aware synchronization around a run.
- Provider-neutral model invocation and cost accounting.

### Out of scope for v0.1

- Unbounded autonomous loops, self-modifying agents, background web crawling, or unsupervised publication.
- Secret storage, provider billing management, model training, or a replacement for Obsidian.
- Treating a worker's prompt/persona as an autonomous system with its own durable authority.

### Ownership

- **GitHub:** canonical, versioned shared repository and history.
- **Local Astraea folder:** execution workspace and checkout.
- **Obsidian:** human-facing interface to the synchronized knowledge workspace; human edits are first-class.
- **AstraeaCore/:** machine-readable operational state, architecture, schemas, run manifests, and audit records.
- **Human:** final authority over sources, claims, durable knowledge, destructive actions, external publication, and policy changes.

The current vault folders, templates, frontmatter conventions, AI isolation concept, and existing Copilot/Obsidian skills are preserved. Existing `sub_agents/` files are agent specifications that may be adapted into registry entries; they are not granted independent autonomy.

## 3. Conceptual data classes

These classes must never be silently conflated:

| Class | Meaning | Examples | Durability |
|---|---|---|---|
| Working context | Inputs assembled for one task attempt | question, plan, selected notes, tool results | ephemeral; hash in run record |
| Persistent memory | Deliberately retained preferences, policies, lessons, and stable facts | user preferences, approved workflow rules | durable; human-reviewable |
| Source material | External or human-origin evidence | paper, URL, PDF, transcript, fleet note | durable; immutable or append-only |
| Derived knowledge | Claims, summaries, atomic notes, maps, and syntheses derived from sources | literature note, atomic concept, final synthesis | durable; provenance required |
| Agent state | Runtime state of a worker attempt | status, cursor, retry count, model, token usage | operational; scoped to run |

Derived knowledge may be revised, but source material is never overwritten to make a conclusion look correct. Working context is not memory merely because a model saw it.

## 4. System shape

```text
Trigger / human request
        ↓
Git boundary + sync preflight
        ↓
Astraea Core: job, policy, budget, registry, scheduler
        ↓
Scout → Researcher → Analyst → Critic → Synthesizer
        ↓                 ↘ validation / approval gates
Draft artifacts + provenance + audit record
        ↓
Git-aware output validation → state update → commit → push
```

Scout, Researcher, Analyst, Critic, and Synthesizer are replaceable workers. Core supplies typed task envelopes and accepts typed result envelopes. A worker cannot schedule another worker, change policy, bypass a gate, push Git, or write outside its granted paths.

## 5. Orchestration lifecycle

1. **Accept:** create a job with `job_id`, request, owner, policy profile, priority, budget, and requested output class.
2. **Preflight sync:** verify repository root, clean-working-tree policy, remote status, lock, and no unresolved conflicts; pull only through the safe sync procedure.
3. **Plan:** Core selects a workflow and creates a bounded DAG. Default research path is Scout → Researcher → Analyst → Critic → Synthesizer; simple note triage may use a shorter path.
4. **Prepare context:** retrieve source material and approved persistent memory, record paths and content hashes, and cap context size.
5. **Dispatch:** invoke one worker attempt through the provider abstraction with explicit permissions, timeout, token/cost budget, and expected schema.
6. **Validate result:** schema, provenance, citations, path policy, claim/evidence linkage, and safety checks. Invalid results are rejected or retried within budget.
7. **Gate:** pause for human approval when the output class, confidence, conflict, or permission policy requires it.
8. **Materialize:** write only approved output to its target staging area; update run state and audit records.
9. **Postflight sync:** validate output, update state, create a conventional commit, and push without force. If push fails, retain the local branch/worktree and stop for recovery.
10. **Complete:** mark success, partial success, rejected, cancelled, or failed with artifact links and metrics.

All transitions are idempotent by `job_id` + `run_id` + `step_id`. A resumed run reuses validated outputs rather than duplicating them.

## 6. Agent registry and responsibilities

The registry is data, not executable autonomy. Each entry declares capability, input/output schemas, allowed tools/paths, provider policy, budget, and human gates.

| Worker | Responsibility | Must produce |
|---|---|---|
| Scout | Clarify the question, identify subquestions, candidate sources, and search plan | bounded research brief and source candidates; no durable conclusions |
| Researcher | Gather and extract source-grounded evidence using approved source tools | source records, quotations/paraphrases, claims, gaps, and provenance |
| Analyst | Compare evidence, map arguments, assess reliability, and derive qualified findings | evidence matrix, reasoning chain, uncertainty, and confidence |
| Critic | Try to falsify, find missing evidence, contradictions, citation errors, and overclaiming | critique with severity and required corrections |
| Synthesizer | Assemble an answer or vault artifact from validated evidence and critique | draft synthesis or note with citations, links, status, and provenance |

Existing specialists such as Atlas, Strategic Researcher, Note Triage Specialist, Vault Architect, and future provider-specific workers can implement one or more registry capabilities. Their files remain replaceable instructions, not identity-bearing services.

## 7. Shared state and persistent memory

Core owns the authoritative run state. Workers receive immutable snapshots plus a task-local scratch area. Shared state is exchanged through versioned envelopes, not hidden model-to-model conversation.

Minimum shared objects: `Job`, `Run`, `Step`, `SourceRecord`, `Claim`, `EvidenceLink`, `Artifact`, `Approval`, `BudgetLedger`, `SyncState`, and `AuditEvent`. Every object has an ID, schema version, timestamps, job/run linkage, and provenance.

Persistent memory is a small, explicit, reviewable store under `AstraeaCore/memory/` (or an equivalent configured location). It contains only approved stable information with owner, scope, confidence, source, created/updated timestamps, and supersession links. No worker may promote working context into memory automatically.

## 8. Knowledge lifecycle

`captured → classified → sourced → extracted → analyzed → critiqued → drafted → human-approved → published/committed → superseded`

Source records retain URL or vault path, retrieval time, content hash, author/publisher metadata when available, and extraction method. Derived notes link to source records and claim IDs in frontmatter or a companion manifest. Uncertainty and disagreement are preserved. Human edits are never overwritten by an automatic regeneration; an agent creates a reviewable patch or draft when a file is human-owned.

## 9. Provider abstraction

Core calls a provider-neutral interface with:

- `provider_id`, `model_id`, capabilities, context limit, and locality/privacy class;
- structured input messages plus tool definitions;
- structured output schema and deterministic request ID;
- timeout, cancellation, retry classification, usage, and cost estimate;
- redaction/data-handling policy and provenance.

Adapters may target DeepSeek, Gemini, local models, or future providers. Worker logic never imports provider SDKs or assumes a model's prompt format. Routing is policy-based: task capability, privacy, latency, quality, and budget. Provider failure may fail over only to an explicitly allowed adapter; failover is recorded and does not silently change privacy policy.

## 10. Tools and permissions

Default deny. Core grants capabilities per step:

- read-only vault search/read;
- source fetch/search, only when the job policy permits network access;
- parse PDF/text/media through approved adapters;
- write to job staging and designated draft paths;
- validate Markdown/YAML/links and provenance;
- Git status/diff/log/fetch/pull/add/commit/push as Core-only operations.

Workers cannot access secrets, arbitrary filesystem paths, Obsidian internals, Git remotes, shell execution, force-push, reset, deletion, or publication unless a separate human-approved capability exists. Source material and sensitive paths may be redacted before external-provider calls.

## 11. Scheduling and triggers

v0.1 supports explicit human invocation and manually enabled schedules (for example, inbox triage or a named research job). File-change triggers are debounced and classified. A commit authored by Astraea is ignored as a trigger for the same job/run; trigger fingerprints and an origin marker prevent recursive loops. Webhooks, queues, and continuous autonomy are deferred.

## 12. Human approval gates

Approval is required for:

- first run of a new workflow/provider/tool policy;
- external network access when not pre-authorized;
- durable edits to `note/atomic/`, `field/`, `project/`, or human-owned literature notes;
- unresolved source conflicts, low confidence, material critic findings, or contradictory evidence;
- memory promotion, deletion, renaming, publication, and policy/registry changes;
- commit/push if the change includes review-required files.

Approval records actor, decision, scope, timestamp, reason, and the exact artifact/content hash approved. Cancellation is safe and leaves drafts plus audit state.

## 13. GitHub/Obsidian synchronization lifecycle

The required lifecycle is:

`pull → validate → execute agents → validate output → update state → commit → push`

Preflight first checks that the configured repository root is exactly the Astraea vault boundary, that the working tree is clean or that human edits are explicitly preserved in a separate review branch/worktree, and that no lock is held by another run. It detects remote changes with fetch plus ancestry/status checks before pulling. Pull is non-destructive and stops on conflicts; Core never force-pushes and never uses destructive reset/checkout.

File classes:

| Class | Examples | Default policy |
|---|---|---|
| Human-owned | `note/fleet/`, active `project/`, manually edited literature/atomic notes | preserve; review-required patch |
| Agent-draft | `AstraeaCore/runs/`, staging, draft outputs | automatic if schema-valid and job-scoped |
| Machine-state | `AstraeaCore/sync-state.json`, manifests, audit records | automatic, serialized, never hand-merged blindly |
| Policy/registry | architecture, decisions, templates, `sub_agents/`, registry | review-required |

Agent-generated changes carry frontmatter or a companion manifest with `origin: agent`, `job_id`, `run_id`, `worker`, `provider/model`, source IDs, content hash, and approval status. Commit messages follow `astraea(<area>): <action> [job:<job_id>] [run:<run_id>]`, for example `astraea(research): add synthesis [job:J-104] [run:R-07]`. Human commits remain human-authored.

After a successful commit, Core records the commit SHA and origin fingerprint before push. A later trigger ignores that SHA/fingerprint for the originating job, while human changes to the same files still create a new review event. Rollback means reverting a specific Astraea commit or restoring a prior file from Git history in a new review commit; it never means resetting the workspace.

If pull fails: stop, preserve local files, record the error, and request conflict resolution. If output validation fails: do not commit; retain the draft and diagnostics. If commit fails: do not push. If push fails: fetch again, verify ancestry, and stop with the local commit preserved for human resolution. Partial runs are resumable from the last validated step.

## 15. Auditability and recovery

Each run emits append-only audit events for trigger, sync checkpoints, context hashes, dispatch, provider/model, tool calls, outputs, validation, approvals, Git SHAs, costs, retries, and failures. Logs may redact content but must preserve identifiers and hashes sufficient to reconstruct what happened from Git history and source records.

Recovery uses bounded retries with exponential backoff for transient provider/tool errors, no retry for policy/schema/permission violations, and explicit human intervention for conflicts or budget exhaustion. A worker failure does not erase prior validated artifacts. Core can resume, replace a worker, or mark the run partial.

## 16. Budgets

Every job has hard ceilings: wall-clock duration, worker attempts, total input/output tokens, provider spend, network calls, source count, and artifact count. Each step receives a sub-budget. Core stops before a hard ceiling, records estimated versus actual usage, and requires approval to continue. Default routing prefers local models for private/low-risk transformations, cheaper models for extraction, and higher-capability providers only when the policy and budget allow.

## 17. Evaluation criteria

v0.1 is successful when a bounded job is reproducible and safe, not when it appears autonomous. Evaluate:

- provenance coverage: every material claim links to a source;
- citation and source fidelity, including quote accuracy;
- critic catch rate and unsupported-claim rate;
- human acceptance/edit distance for durable notes;
- schema/link/frontmatter validation pass rate;
- idempotency and duplicate-run rate;
- sync safety: no lost human edits, no force-push, conflict detection accuracy;
- recovery success after provider, pull, push, and validation failures;
- latency, token use, spend, and budget adherence;
- provider interchangeability using the same worker contract.

Evaluation fixtures should include conflicting sources, malformed notes, remote changes, simultaneous human edits, repeated agent commits, provider timeout, and budget exhaustion.

## 18. Unresolved architectural questions

1. What exact GitHub repository and branch are canonical, and should the vault become its own repository rather than inheriting a parent repository?
2. Which Obsidian synchronization mechanism is authoritative when edits happen concurrently on multiple devices?
3. Should machine state be committed to the shared repo, or split into a private operational branch/repository?
4. What redaction and data residency policy applies per field, source, and provider?
5. Which structured artifact format should accompany Markdown: JSON sidecars, frontmatter only, or both?
6. How should semantic duplicate detection work without turning embeddings into an unreviewable source of truth?
7. Which schedules are useful enough to enable, and what device/credential availability guarantees do they require?
8. What approval UI should show a human diff, provenance graph, cost, and critic findings together?
9. What retention period and access control apply to prompts, tool outputs, and audit logs?
10. How should provider quality be benchmarked across models with different context and tool capabilities?

## 19. Roadmap

### v0 — safe, bounded foundation

- Confirm repository boundary and GitHub remote; add preflight validation.
- Define schemas for registry, jobs, runs, source/claim/evidence/artifact, approvals, and sync state.
- Implement one explicit, human-invoked workflow with Scout → Researcher → Analyst → Critic → Synthesizer.
- Use staged drafts, read-only source access, provider adapters, hard budgets, audit records, and review-required durable edits.
- Add pull/validate/execute/validate/commit/push with conflict and loop prevention.

### v1 — dependable orchestration

- Add resumable DAG execution, retries, worker replacement, schedule triggers, and a review dashboard in Obsidian.
- Add multiple providers including a local model and policy-based routing/failover.
- Add provenance-aware search, duplicate detection, regression fixtures, and cost/quality reports.
- Support safe multi-device sync and clearer ownership metadata for human versus agent files.

### v2 — supervised autonomy

- Add event-driven research queues, bounded multi-job scheduling, and adaptive planning within policy limits.
- Add richer evidence graphs, memory promotion workflows, provider benchmarking, and selective autonomous low-risk maintenance.
- Keep human gates for durable knowledge, policy changes, publication, deletion, and unresolved disagreement.
