# Durable Core v0.2

The computational Core retains its provider-independent, five-role workflow. The optional durable service adds restart-safe operational storage; the vault reader captures immutable knowledge snapshots from GitHub. All examples and tests are intended for cloud execution.

## Verify in a cloud checkout

```sh
node "Astraea III/AstraeaCore/test/run.mjs"
node --test "Astraea III/AstraeaCore/test/durable.test.mjs" "Astraea III/AstraeaCore/test/github-reader.test.mjs"
node "Astraea III/AstraeaCore/examples/demo.mjs"
```

No package installation or model credentials are needed. SQLite tests use the Node built-in module, which may emit an experimental-feature warning on supported Node releases. Production runtime selection should account for that status.

## Durable API

```js
const store = await SqliteJobStore.open({
  directory: "/approved-cloud-volume/astraea-state",
  forbiddenRoots: ["/cloud-checkout"]
});
const service = new DurableAstraea({store, registry, providers, leaseMs: 60000});
service.submit(job); // acknowledged transaction; an identical submission returns its prior state
const run = await service.execute(job.runId);
await service.review(run.id, {actor: authenticatedHuman, artifactHash: run.artifact.hash, decision: "approve"});
store.close();
```

Imports are from src/sqlite-store.mjs and src/durable-core.mjs. The path and volume above are illustrative and are not provisioned by this code or this development task. Supply every checkout/vault boundary in forbiddenRoots. Storage must be outside them, private, persistent and accessible to the cooperating cloud processes. No database is installed automatically.

Rows contain normalized job/source snapshots, step outputs, approvals, budget ledger and audit events. Each committed revision is retained in history. Transactional event uniqueness spans run IDs and process restarts. No automatic ledger eviction, retention cleanup or schema migration occurs.

Every execution/review/cancel operation acquires a renewable lease with a monotonically increasing epoch. Checkpoint saves compare both the revision and the unexpired epoch. After lease expiry, a new executor can recover; an old executor cannot save, dispatch a subsequent step, or release the new lease. Set leaseMs comfortably above normal request latency. Wall-clock/host scheduling assumptions apply; all executors need the same durable SQLite file and host clock. This is not a multi-region scheduler or a network-database replacement.

Before dispatch, the request and its full token/cost reservation are committed. After restart:

- A queued job runs normally.
- A validated completed prefix is reconstructed and skipped; request IDs stay stable.
- An interrupted in-flight step becomes needs_reconciliation, keeps its budget reservation and is never automatically dispatched again.
- Terminal drafts/approvals/rejections/cancellations replay without provider calls.

Checkpoint restoration revalidates job/registry identity, source content, context/output hashes, evidence, step ordering, usage, critique gates, artifact content/provenance and approvals. A checksum protects stored JSON from accidental corruption. Unknown schemas fail closed. A persistence failure halts immediately and leaves the last acknowledged checkpoint authoritative.

The default Core instance still supports in-memory use. Durable guarantees apply only through DurableAstraea and a persistent shared store. Provider adapters remain trusted code; they must enforce budget caps/cancellation. There is no automatic retry of uncertain requests, automatic lease-driven provider cancellation, or human reconciliation endpoint yet.

## Read-only GitHub / Obsidian knowledge interface

```js
const reader = new GitHubVaultReader({getJson: githubGetJson()});
const snapshot = await reader.openSnapshot();
const source = await reader.readSource(snapshot.commit, "Astraea III/field/cs.md.md", {id: "S1"});
```

Imports are from src/github-reader.mjs. The adapter reads only the canonical repository's main branch metadata, pinned tree and selected blobs through fixed GitHub GET endpoints. A token may be passed explicitly to githubGetJson when required; it is never read from a laptop or persisted. Transport failures are redacted, redirects are refused, deadlines/response sizes are bounded.

Only regular Markdown files under note/fleet, note/lit, note/atomic, field and project are readable. Hidden/config/operational paths, symlinks, truncated trees, invalid UTF-8, oversized blobs and content that does not match its Git blob hash fail closed. Both .md and existing .md.md names work. The resulting source retains repository/commit/blob provenance, SHA-256, privacy, retrieval method/time and exact Unicode text (including UTF-8 BOM when present).

This reads Obsidian-compatible files from the synchronized GitHub workspace. It never opens Obsidian, accesses a laptop, reads unsynced local edits, pulls/fetches a checkout, changes Git refs, or asserts that a working tree is clean. Existing Git policy preflight remains a separate boundary for a future writer. The current implementation offers no Git or vault mutation capability.

## Operational limits

SQLite WAL requires suitable local persistent cloud storage and supported locking/fsync semantics; do not use an unsupported network filesystem. Back up/checkpoint the complete database consistently, including WAL state, using an operator-approved process. Backup/restore automation is a next milestone. Checkpoints contain private source text; directory/volume access, encryption and authenticated approval identity belong to the cloud host.

Checksums do not authenticate a malicious store operator. Lease clocks, disk quotas, retention and provider outcome reconciliation still need production policy. There is no deployment, scheduler, external model, persistent semantic memory or approved-write integration in this milestone.
